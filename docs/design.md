# Webapp 設計書

## 1. 概要

新規Webアプリケーションの設計書。現時点ではアプリの詳細な目的は未確定のため、
まず以下の2画面を対象としたシステム構成・アーキテクチャを定義する。

- ログイン画面: ID・パスワードによる認証
- ホーム画面: 詳細は未定（今後追記）

デザイン（見た目・UI）は本フェーズでは対象外とし、機能面の設計を優先する。

## 4. 認証設計

### 4.1 ログインフロー

1. ユーザーがログイン画面でID・パスワードを入力し送信する
2. サーバー（Route Handler）がPostgreSQLのユーザーテーブルと照合する
   - パスワードはハッシュ化（例: bcrypt）して保存し、照合時もハッシュ同士で比較する
3. 認証成功時、`{ userId, 有効期限 }` を含むトークンをサーバー側の秘密鍵でHMAC署名し、`httpOnly` なCookieとしてブラウザに保存する
4. 以降のリクエストでは、Cookie内のトークンの署名を検証し、有効期限内であればログイン状態と判定する

サーバー側にセッション状態を保持しない、ステートレスな方式とする。
Vercelのようなサーバーレス環境ではリクエストごとに別インスタンスが処理する可能性があり、
インメモリのセッションストアだと直前にログインしたはずなのに未ログイン扱いになる不具合が起きるため、
Cookie自体に検証可能な情報を持たせる方式に変更した。

### 4.2 ログイン状態の保持

ログイン画面での選択は設けず、常に有効期限を長く設定した永続的なCookie（30日）とする。
一度ログインすればブラウザを閉じて再度開いてもログイン状態が維持される。

### 4.3 ログアウト

- `/api/logout` 呼び出し時にCookieを削除する（トークン自体はステートレスなため、サーバー側の破棄処理は不要）

## 5. 画面設計

### 5.1 ログイン画面

| 項目 | 内容 |
|---|---|
| 構成要素 | ID入力欄、パスワード入力欄、ログインボタン（ログイン状態は常に保持） |

### 5.2 ホーム画面

札幌市電の路線図を中心に配置し、事件が紐づく3駅にのみマーカー（色付き丸）を表示する探偵ゲーム風の画面。

#### 5.2.1 路線図

- 札幌市電の公式路線図（ループ線、全24駅）の形状に近いSVGを自前実装で描画する
- 全24駅を路線図上に描画するが、大きく色付きで表示しクリックできるマーカーは対象の3駅にのみ表示する。それ以外の駅は小さな目印（グレーの点）として表示するのみとする
- マーカーや駅名ラベルが窮屈にならないよう、路線図全体を余裕のあるサイズで描画する

#### 5.2.2 対象の3駅（事件発生駅）

| No. | 駅名 | 備考 |
|---|---|---|
| 1 | 電車事業所前 | |
| 2 | 中島公園通 | |
| 3 | 西15丁目 | 確定（変更なし） |

※ 狸小路は周辺の駅（すすきの等）と近接して窮屈になるため、対象から除外した。

#### 5.2.3 マーカーの色分け

事件のステータスに応じてマーカーの色を変える。

| ステータス | 色（案） |
|---|---|
| 未解決 | 赤 |
| 捜査中 | 黄 |
| 解決済み | 緑 |

※ ステータスの種類・呼称は上記を仮案とする。確定後に修正する（[今後の検討事項](#7-今後の検討事項)参照）。

#### 5.2.4 マーカータップ時の挙動

マーカーを1回タップ（クリック）すると、その駅に紐づく事件の簡易情報をポップアップ表示する。

ポップアップに含める項目:

- 事件タイトル
- ステータス（未解決／捜査中／解決済みなど）
- 事件概要（詳細本文ではなく、要約した文章）
- 「解決する」ボタン → 押下でその事件の詳細ページへ遷移

#### 5.2.5 「解決する」ボタンの遷移先

利用規模は約50人程度と小規模なため、駅（事件）ごとに個別のページを作り込むのではなく、
**1つの共通テンプレートページ（動的ルート）を使い回す軽量な構成**とする。

- ルート例: `/case/[caseId]`
- `caseId` に応じてDB（PostgreSQL）から該当事件のデータを取得し、同一テンプレートで描画する
- ページ数を増やさず実装・保守コストを抑えつつ、駅ごとに異なるURLを持たせられる
